# Change Report: Core PDF Workflow Performance

## Scope

- Goal: establish a reproducible baseline, identify measured bottlenecks, and improve local
  PDF processing without changing page order, page selection, output validity, or OCR behavior.
- In scope: PDF compression, PDF-to-Word page-image conversion, PDF preflight, a synthetic
  benchmark harness, regression tests, and this report.
- Out of scope: Unlimited-OCR, GPU/model performance, installer lifecycle, UI redesign, and
  parallel processing.
- Baseline: detached commit `651a93c` (`Prepare v0.6.0-beta.4 release`).
- Candidate: the working-tree changes described in this report.

## Environment

- Host: Windows 11 `10.0.26200`, Intel Family 6 Model 183, 20 logical CPUs.
- Python: 3.12.12 from the existing project `.venv`.
- PyMuPDF: 1.26.7.
- Pillow: 12.3.0.
- Benchmark data: synthetic local PDFs generated by
  `scripts/benchmark_core_workflows.py`; no user documents or network access.

The A/B run used the same Python environment and benchmark harness for both revisions. Each
scenario ran two warm-ups followed by seven measured samples. The table reports the median,
not the fastest sample.

## Results

| Scenario | Fixture | Baseline median | Candidate median | Relative change | Baseline output | Candidate output |
|---|---:|---:|---:|---:|---:|---:|
| Compress PDF | 8 image pages, 1600x2200 each | 2.080 s | 1.441 s | 30.74% faster | 917,625 B | 917,624 B |
| PDF to Word - Page Images | Same 8-page image PDF | 1.141 s | 1.047 s | 8.24% faster | 2,670,549 B | 2,427,366 B |
| PDF to Word - Text Only | 120 text pages | 0.178 s | 0.174 s | 2.31% faster | 45,970 B | 45,970 B |
| PDF to Images control | Same 8-page image PDF | 0.847 s | 0.868 s | 2.47% slower | 2,471,678 B | 2,471,678 B |

The PDF-to-Images implementation did not change. Its 2.47% movement provides a practical noise
reference for this host. The compression improvement is about twelve times that control
movement, and the page-image improvement is about three times that movement.

The PDF-to-Word page-image DOCX became 9.11% smaller. The regression test opens the embedded
PNG and compares every RGB byte with the source PyMuPDF pixmap, so the size reduction does not
come from lossy rendering.

## Profile Findings

### PDF compression

The baseline profile spent 1.277 of 1.893 seconds in image optimization. For eight
Flate-backed images, `extract_image` used 0.653 seconds; 0.555 seconds of that work encoded an
intermediate PNG. Pillow then decoded the PNG, resized the pixels for 0.474 seconds, and encoded
a full JPEG candidate for 0.139 seconds. The exact comparison rejected those JPEG candidates
because the existing lossless representation was smaller.

The candidate reads pixels directly from the PDF image xref. For an unfiltered image, the
compressor estimates the stream size that `doc.save(..., deflate=True)` will create. A 400-pixel
preview estimates the JPEG candidate size. The compressor skips the full Lanczos resize and
full JPEG encode only when the preview estimate is at least 1.5 times the source estimate;
borderline candidates still use the existing exact full-size comparison.

The candidate profile spent 0.803 of 1.406 seconds in image optimization. The intermediate PNG
encode disappeared. The remaining measured costs were 0.476 seconds for the conservative zlib
source-size comparison and 0.109 seconds for preview estimation.

### PDF-to-Word page images and preflight

The baseline page-image profile spent 0.457 of 1.109 seconds in Pillow PNG encoding after
copying each rendered pixmap into a Pillow image. The candidate passes PyMuPDF's native PNG
bytes directly to `python-docx`. The A/B run measured an 8.24% latency reduction and a 9.11%
DOCX size reduction.

The baseline PDF-to-Word path also opened a PDF repeatedly for validation, page-range parsing,
and text sampling. `_inspect_pdf` now validates the document, parses page indices, and samples
text during one open operation. The public `preflight_pdf` and page-range behavior remain
unchanged.

## Files Changed

### Added

- `scripts/benchmark_core_workflows.py`: creates deterministic fixtures, validates outputs,
  records repeated timings, and optionally writes JSON and cProfile data.
- `docs/performance/core_workflow_benchmark.md`: records the method, evidence, results, and
  verification boundary.

### Modified

- `src/handlers/pdf.py`: removes the intermediate PNG round trip and rejects clearly
  unprofitable full JPEG candidates from a bounded preview.
- `src/tools/pdf2word/tool.py`: uses native pixmap PNG bytes and consolidates PDF inspection.
- `tests/test_workflows.py`: verifies the optimized compression path, pixel-identical DOCX
  media, and single-open preflight behavior.
- `README.md`: links this maintained benchmark report from the development section.

### Deleted

- None.

## Design Decisions

- The benchmark creates fixtures before the timed region and validates artifacts after it.
- The compression preview is a rejection fast path, not a replacement for the existing exact
  size check. A 1.5x margin sends uncertain cases through the full encoder.
- Unfiltered image streams use zlib size because the final PDF save applies `deflate=True`.
  Already-filtered streams use their existing raw stream size.
- JPEG quality, maximum image dimensions, transparent-image handling, page order, page ranges,
  OCR selection, and CLI/GUI entry points did not change.
- The project gained no dependency; the harness uses existing runtime and standard-library
  modules.

## Reproduce the Benchmark

From the repository root on Windows PowerShell:

```powershell
uv run --no-sync python scripts/benchmark_core_workflows.py --repeat 7 --warmup 2
```

Profile one scenario and retain machine-readable output:

```powershell
uv run --no-sync python scripts/benchmark_core_workflows.py `
  --scenario compress_pdf `
  --repeat 7 `
  --warmup 2 `
  --profile compress_pdf `
  --profile-out tmp/compress.prof `
  --json-out tmp/compress.json
```

Run the benchmark on an idle machine and compare medians from the same host, Python environment,
fixture configuration, warm-up count, and repeat count.

## Known Limitations

- Synthetic fixtures isolate the measured code paths but do not represent every PDF image
  codec, color space, page layout, storage device, or antivirus configuration.
- The results do not make a latency claim for OCR, GPU inference, installers, or arbitrary user
  documents.
- Scripted headed-GUI checks rendered all 11 tool panels, and the Document OCR GUI completed a
  real Tesseract run. The checks did not manually exercise every input combination, drag-and-drop
  route, conflict dialog, or Windows file association.
- The optional Unlimited-OCR stack was inspected but not installed or run. Its setup requires an
  approximately 12 GB model download, additional disk space, and explicit trust for model code.
- The installer compiled successfully, but install, upgrade, uninstall, and retained OCR-data
  behavior were not exercised on this workstation. Those lifecycle checks require a disposable
  Windows VM or test machine.
- The PDF-to-Images control varied by 2.47%; changes near that magnitude should be treated as
  host noise until another controlled run reproduces them.

## Rollback

The performance work has three patch boundaries: the benchmark/report, PDF compression, and
PDF-to-Word conversion. Reverting the corresponding files restores the baseline behavior; no
data migration, configuration migration, cache cleanup, or dependency rollback is required.

## Required Follow-Up

- Run the same harness on representative non-private PDFs before making a general end-user
  performance claim.
- Run installer install, upgrade, uninstall, and retained-data checks in a disposable Windows
  VM or test machine before promoting a release candidate.
- Install and evaluate the optional Unlimited-OCR stack only after explicit approval of its model
  download, disk use, and custom-code trust boundary.
